Mission Dashboard — Archaeology & Migration

The dashboard was never deleted. What regressed is thread isolation, backpressure, and crash safety — and the symptom on screen right now traces to a different, already-known bug entirely.

00

Field findings — read this first

Three things are true simultaneously, and conflating them will misdirect the fix:

Verdict
01

The dashboard was not deleted. It exists in every version, V30 through the current v32_flight_stack, and is constructor-wired into all three live entrypoints today.

02

What actually regressed is architectural, not presence/absence. V30/V31's dashboard ran on a dedicated thread behind a bounded queue with crash isolation. v32_flight_stack's Dashboard runs synchronously, unisolated, inside the mission's own coroutine.

03

The reported symptom — “mission starts, drone takes off, dashboard never opens” — has a precise root cause that is neither of the above. It's the still-open upload_mission() empty-mission bug identified earlier this engagement: it causes the only loop that ever calls dashboard.update() to never run at all.

Fixing the dashboard-open symptom today requires fixing upload_mission(), not the dashboard. Fixing the dashboard architecture — restoring V30/V31's isolation guarantees inside v32_flight_stack — is a separate, still-necessary migration, detailed below.

01

Investigation method

Comparative, evidence-first, no assumptions: byte-level diff of debug_view.py and main.py across v31_3rd_mission/ and v32/; grep for dashboard/viewer/EventBus symbols across every version directory and v32_flight_stack; direct reads of mission_types.py, debug_view.py, core/telemetry/dashboard.py, both orchestrators, master_fsm.py, and all three main_*.py entrypoints; ast.parse against the flat v32/main.py to verify a suspected syntax defect; the three run_mission_v32_*.sh launchers to determine what actually executes; git log for commit-level attribution.

Git history disclosure
.scripts/olds/ (V30 through v32_flight_stack) entered this repository in a single commit — c5eb734e5a, “Initial import: modified PX4 (Kursad edition) + scripts,” 2025-11-27. There is no incremental history showing the V30→V31→V32 evolution. The requested “which commits/refactors caused it” cannot be answered from commit history — none exists. The findings below are reconstructed from structural file-tree comparison instead, which is conclusive on its own.

2.1The isolation properties that mattered most

debug_view.py:400-482 — all real cv2 work happens on a dedicated thread; the flight loop's only contact with it is a non-blocking, bounded-queue put():

debug_view.py — UIWorker
class UIWorker:
    """Dedicated thread for rendering OpenCV UI to prevent blocking the flight loop."""
    def start(self):
        self.thread = threading.Thread(target=self._run, daemon=True)
        self.thread.start()

    def update(self, snapshot: UISnapshot):
        # this runs directly on the main mission loop's thread, so it
        # must never raise: an unhandled exception here would take the
        # mission down with it, not just the dashboard.
        try:
            self.snapshot_queue.put(snapshot, block=False)
        except queue.Full:
            self.dropped_snapshots += 1  # drop-oldest, keep the flight loop at rate

    def _run(self):
        while self.running:
            try:
                snapshot = self.snapshot_queue.get(timeout=0.05)
                self.debug_view.draw_dashboard(snapshot, ...)
            except queue.Empty:
                pass

This is exactly the “mission runtime must never block on the Ops Center” property ADR-004 (§1, §13) proposed as new. It already existed. It is what got lost. main.py's own call site adds a second, independent layer: the entire snapshot-construction-and-update block is wrapped in its own try/except, commented “a bug in snapshot construction or rendering can never take the mission loop down with it.”

05

Root cause of the reported symptom — traced, not inferred

Full call chain, gorev2_orchestrator.py:

  1. run() connects, arms, takes off to MISSION_ALTITUDE_M — this is the part observed working.
  2. upload_mission(waypoints) is called with 5 real waypoints, but the backend (mavsdk_backend_base.py:80-84) discards the argument and uploads an empty MissionPlan([]) — already identified this engagement, fix not yet applied.
  3. start_mission() starts the empty mission.
  4. For an empty mission, is_mission_finished() returns True on the very first check (current == total == 0).
  5. The loop body never executes. self.dashboard.update(...) lives entirely inside that loop. cv2.namedWindow/cv2.imshow are never reached. No window opens.
Falsifiable
Applying the upload_mission() fix already proposed this engagement is, on its own, sufficient to make the dashboard window appear — independent of anything else in this report.
06

Secondary, latent regression

Once §5 is fixed and the loop begins running, self.dashboard.update(...) executes every tick with no surrounding exception handling — unlike either V30/V31 isolation layer. cv2.imshow/cv2.waitKey are not guaranteed to succeed in every deployment environment (headless companion computer, missing Qt platform plugin, SSH without X forwarding). If they raise, the exception propagates out of Gorev2Orchestrator.run() and terminates the entire mission coroutine — mid-flight.

Directly contradicts the stated requirement
“The Mission Dashboard is NOT a mission controller… it is an observer.” Today, a rendering failure isn't just an observer going dark — it can end the mission. This is the most safety-relevant single finding in this report; top migration priority once §5 is fixed.
07

Adjacent finding — Mission Complete / Görev 3 is unreachable regardless

MasterMissionController is the only component that sequences Görev 2 → Görev 3 → land — the only path by which “dashboard remains active through the whole mission, then transitions into Mission Complete” could occur end-to-end. A repository-wide search shows it is referenced only inside the file that defines it — none of the three live entrypoints construct or run it. Each calls asyncio.run(orchestrator.run()) directly on a bare Gorev2Orchestrator.

Today a mission ends when Gorev2Orchestrator.run() returns, with no explicit MISSION_COMPLETE transition and no graceful dashboard handoff. This is independent of the dashboard investigation but blocks part of the required behavior until MasterMissionController is wired into an entrypoint — a mission-sequencing decision this report flags but does not resolve.

08

Target architecture — restoring V30/V31's guarantees inside v32_flight_stack

Not “copy UIWorker back in.” v32_flight_stack has a real interface-driven architecture V30/V31 didn't — the migration must fit that shape.

8.1Preserved from V30/V31 — proven, not experimental
  • A pub/sub event model — the same mechanism ADR-004 §12 specified as new; correctly understood here as restoring a pattern that already shipped, not inventing one.
  • A dedicated rendering thread fed through a bounded, drop-oldest queue — UIWorker's core technique, directly reusable.
  • Two-layer crash isolation: the publish call site never raises, the render thread's own failures never reach the mission coroutine.
  • A structured, typed snapshot as the single object the renderer consumes.
8.2What must change to fit v32_flight_stack, not be reintroduced as-is
  • UISnapshot was built for V30/V31's string-based state model. It must be re-derived from v32_flight_stack's real objects — and converge with ADR-004's MissionSnapshot rather than compete with it.
  • event_bus was a bare module-level global — a coupling smell in the interface-driven v32_flight_stack. It becomes an injected constructor dependency, same pattern already used for flight/camera/detector/actuator.
  • DebugView's 9-panel layout is reusable presentation logic almost as-is — only what populates the snapshot changes, not how the panels draw.
  • Gorev3Orchestrator already accepts a dashboard param — no new coupling needed there; it's MasterMissionController (§7) that needs to exist as a live entrypoint for that wiring to matter.

Event flow (target state)

Sequence
RUN MISSION (operator runs run_mission_v32_*.sh)
  -> main() builds flight/camera/actuator/detector via existing DI pattern
  -> main() constructs the dashboard's publisher + render-thread pair
  -> render thread .start()'d -- UNCONDITIONALLY, before orchestrator.run()
      (matches V30/V31's "automatic, no operator action" behavior)
  -> orchestrator runs; every tick:
       - derive a snapshot from live subsystem state
       - publish it -- non-blocking, bounded queue, drop-oldest
  -> render thread consumes independently, draws, shows
  -> on reaching MISSION_COMPLETE / FAILED / ABORTED:
       - a terminal snapshot is published
       - render thread stays alive briefly in "Mission Complete" mode
       - then .stop() from the same finally: pattern main.py uses today

Required changes — descriptive, no implementation here

  1. Fix upload_mission() — already scoped this engagement, required before any dashboard change is even observable.
  2. Wrap both orchestrators' dashboard-update call sites in isolation — restore thread+queue (preferred, matches proven design) or, as a stopgap, wrap the existing synchronous call in try/except. The stopgap alone doesn't fix the async-loop-blocking problem.
  3. Introduce a snapshot type derived from v32_flight_stack's real subsystems, converging with ADR-004's MissionSnapshot.
  4. Introduce an injected publish mechanism, replacing the bare event_bus global with a constructor-injected dependency.
  5. Port DebugView's panel-drawing logic, retargeted to the new snapshot type.
  6. Resolve the MasterMissionController gap (§7) — prerequisite for Mission Complete continuity; a sequencing decision, not a dashboard change.
  7. Archive or fix the flat v32/ directory's SyntaxError — not required for the dashboard fix, but currently a landmine for anyone who assumes it's live, exactly the confusion this investigation had to resolve first.

14

Compatibility analysis

  • Backward compatibility with V30/V31: not a goal — nothing outside their own directory imports UISnapshot/event_bus.
  • Compatibility with v32_flight_stack's DI pattern: required and achievable — the dashboard publisher slots into the same constructor-injection pattern every other subsystem already uses.
  • Compatibility with Gorev3Orchestrator's existing dashboard parameter: already compatible — no signature change needed there.
  • Compatibility with ADR-004: requires the explicit convergence in §8 — building this in isolation would produce two parallel, divergent observability systems in the same codebase.
  • Compatibility with the three run modes: the dashboard publisher should follow the same single-instance-shared-across-backends pattern DualFlightBackend already uses, not be duplicated per backend.
