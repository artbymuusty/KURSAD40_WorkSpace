00

Why this document exists

Twice in this engagement, the vehicle appeared to do nothing — “climbs to 15 m, then hovers” — for two completely different root causes. In both cases, no error, no warning, no log line said “the mission cannot proceed.” The system was in a state indistinguishable from normal operation.

Field evidence — this engagement
01

TargetValidator.is_validated() required a condition (is_navigating_to) that no code path ever set. The detection → centering → drop pipeline was permanently unreachable, and nothing reported it.

02

MavsdkBackendBase.upload_mission() silently discarded the generated waypoints and uploaded an empty mission. PX4 had nothing to fly, and is_mission_finished() reported True immediately (0 == 0), skipping the entire mission loop.

Diagnosing each took a full manual code trace — exactly what the current Dashboard (a synchronous cv2.imshow HUD bolted into the hot loop) cannot help with: it draws bounding boxes on video, nothing about mission state, blocking conditions, or subsystem health. This ADR exists so that gap closes permanently.

01

System philosophy

No silent waits. Every point where the mission runtime is blocked must have a name, an owner, a start time, and — where applicable — a timeout.

State is a first-class object, not a side effect of control flow. Today, “what phase is the mission in” is answerable only by knowing which line of Gorev2Orchestrator.run() the interpreter is currently executing. The mission state must be an explicit, queryable data structure that drives control flow and is what the Ops Center reads — one source of truth, not a UI reconstruction of logs.

Observability is not logging. Logging is one consumer of the event stream, not the mechanism. The runtime publishes structured events; logging, the Ops Center, replay, and analytics are independent subscribers to the same stream.

The mission runtime must never block on the Ops Center. Dashboard.update() calls cv2.imshow/cv2.waitKey synchronously inside the detection loop today. If a display window hangs or isn't attached in the field, the mission stalls with it. Telemetry publication must be fire-and-forget.

Every subsystem proves it is alive, not just that it hasn't crashed. A component that stops producing output — camera frozen, detector stuck loading a model, MAVSDK connection silently dropped — is functionally a failure and must be treated as one, via heartbeats and staleness detection, not exception handling alone.

Design for the postmortem, not just the live view. Every event is durable and replayable. A competition run's full mission history must be reconstructable after the fact, without the aircraft.

Minimal-diff integration. Existing business logic (Gorev2DurumMachine, PayloadInterlock, PositionStore) is materially correct after this engagement's two fixes and is not rewritten to accommodate observability. Instrumentation is added at existing seams, not by inverting control.

02

Scope & non-goals

In scope: runtime architecture for mission state, event streaming, health/watchdog monitoring, blocking-reason capture, logging, diagnostics, replay, and integration with existing v32_flight_stack modules.

Explicitly out of scope: visual design, UI framework, React/Flutter/HTML, network transport security hardening, multi-vehicle swarm coordination (touched only in §21 as a forward-compatibility note). No code is written here; every identifier below refers to the current, real source, so this document is falsifiable against the repository — not aspirational.

04

The core correction — explicit mission state

Today, mission “state” is implicit: Gorev2Orchestrator.run() is one long async def where progress is encoded as which await the coroutine is suspended on, plus local booleans (gorev2_tamamlandi, current_state_text). Gorev2DurumMachine is not the mission state machine the Görev 2 report calls for — it only covers the DURUM-1..4 payload-priority decision. No object anywhere answers “what phase is the mission in right now” without reading a log tail.

Correction: introduce an explicit MissionPhase enum and a MissionContext object that is mutated only through named transitions (context.transition_to(phase, reason)), is what the orchestrators hold and update, is published to the EventBus on every transition, and is queryable synchronously at any instant (context.snapshot()) — so a late-attaching Ops Center can render current state without replaying history.

This single change is what makes “why isn't the drone moving” mechanically answerable: the answer is always context.current_phase + context.blocking_reason (§8), not a code trace.

Required distinction
Two categories must be tagged explicitly in BlockingState: EXPECTED_WAIT (correctly blocked by design) vs. BLOCKING_WAIT (acceptable only up to a timeout). The current codebase has zero instances of the second category actually enforcing a timeout — the single most important behavioral gap this ADR closes.

Subsystem integration matrix

9.1Flight Backend — IFlightBackend → GzFlightBackend / RealFlightBackend / DualFlightBackend
  • Exposes connection state, armed state, flight mode, position, attitude, mission progress.
  • Metrics telemetry update rate, command round-trip latency, position age.
  • Health check last telemetry sample < 1s old; connection state == connected.
  • Gap drone.telemetry.health() (EKF / GPS-fix / pre-arm checks) is available from MAVSDK today and is never called anywhere in the codebase.
9.2Vision Pipeline — YoloDetector, TargetValidator, TargetSelector
  • Exposes model-loaded state, per-frame detections, per-shape tracking state, selection outcome.
  • Metrics effective Hz — must validate against config bounds CAMERA_PROCESS_FREQ_HZ_MIN/MAX = 10/30, currently unmeasured.
  • Health check model loaded and last frame within staleness window.
9.3Navigation / Visual Servo — CenteringController
  • Exposes current pursuit target, pixel error, convergence state, gain values (kp_horizontal/kp_vertical — currently placeholders per the TODO[KONTROL] in source).
  • Metrics time-to-converge, pixel-error trend, target-lost recoveries.
  • Health check while active, error must be decreasing — a timeout with no progress is a fault, not just an expiry.
9.4Payload Subsystem — PayloadInterlock, PayloadReleaseService, actuator implementations
  • Exposes interlock state, release-in-progress state, verification outcome.
  • Errors mark_payload_2_released() raising RuntimeError is the interlock working correctly — must never be silently swallowed, must be CRITICAL, not just an exception.
9.5MissionMemory — PositionStore, MissionCheckpoint
  • Exposes all saved TargetPoints, checkpoint coordinates, save/rejection history.
  • Errors checkpoint-not-saved is a hard RuntimeError from MissionCheckpoint.get() — correct, but must also be a CRITICAL event so an operator sees it on screen, not in a stack trace.
9.6Search Planner — does not exist as a named component today

Gorev2Orchestrator._generate_square_mission() is a private method embedded in the orchestrator, not an independent, observable component. Recommendation: extract a SearchPlanner class (generate(center, size) → list[Waypoint]) so route generation is independently observed (a real ROUTE_GENERATED payload, not implied by upload) and swappable later — this is also the correct seam for a future QGC-sourced polygon strategy, which this ADR does not add.

9.7Configuration — core/config/parameters.py

Exposed as a versioned snapshot attached to mission_id at startup, so replay knows exactly which thresholds were active. Health check: no required-for-current-phase parameter is still None (e.g. NORMAL_MISSION_SPEED_M_S, GOREV3_TRANSIT_SPEED_M_S).

Health model

StateMeaning
Healthyheartbeat/output within cadence, no active warnings
Degradedoperating but outside nominal parameters (e.g. detection Hz below 10)
Staleexpected heartbeat missed once, within grace period
Downheartbeat missed beyond grace period, or a dependency is DOWN
Unknownnot yet initialized — no data since mission start

The Health Monitor computes state purely from event timestamps and declared cadences — subsystems don't self-report health, they just keep emitting on schedule. Going silent is the signal. Dependency propagation: if Flight Backend is DOWN, Navigation and Payload are forced DOWN too, regardless of their own last heartbeat — their outputs are meaningless without it. This requires the dependency graph in §11 to be encoded, not just documented.

12

Observability architecture — EventBus

  • Transport (v1) in-process asyncio.Queue pub/sub, one publisher (the mission runtime), multiple subscribers (Aggregator, Health Monitor, Watchdog Engine, Logging Sink, Event Store). No network hop required — runtime and Ops Center already share the GCS host.
  • Publish contract publish(event) is synchronous-to-call, asynchronous-to-deliver — bounded queue, drop-oldest-and-count-drops policy, so a slow subscriber can never back-pressure the mission runtime. A dropped event still emits a meta-event (EVENTBUS_BACKPRESSURE_DROPPED), so drops are themselves observable.
  • Durability boundary the Event Store subscriber is the system of record for replay (§19), independent of whether live subscribers were attached.
  • Why not a broker in v1 current deployment is single-process, single-host, single-vehicle. A broker adds a failure mode — broker down ⇒ blind mission — with no present benefit. §21 revisits this for multi-vehicle/remote-viewer scenarios.
13

Mission Operations Center architecture

Three internal roles, each an independent EventBus subscriber, each individually restartable without affecting the mission runtime or each other:

  1. Runtime State Aggregator — folds the event stream into the live MissionSnapshot. Only component allowed to mutate the snapshot.
  2. Watchdog Engine — owns all timers from §18, independent of the Aggregator, so a frozen Aggregator cannot mask a watchdog firing.
  3. Health Monitor — computes the health matrix from heartbeat cadence, independent of both.

A Presentation Layer (explicitly out of scope) reads MissionSnapshot, subscribes to live events, and queries the Event Store for history. It has zero business logic: no subsystem should ever require it to be running to function correctly.

Auto-open requirement: “RUN MISSION” issuing the mission-start command is itself the first MISSION_STARTED event; the launcher is responsible for also starting/focusing the Ops Center process. This is process-supervision, out of scope here — but the architectural hook is that MISSION_STARTED is unambiguous and machine-detectable the instant it happens, not inferred from telemetry.

14

Integration architecture

Minimal-diff, per philosophy §1:

  • Every constructor in core/mission/*, core/navigation/*, core/detection/* gains one injected dependency: a publisher: EventPublisher, with a default no-op implementation so tests and the mocks in tests/mocks/ require zero changes.
  • Existing logger.info/logger.warning call sites are not deleted — each is paired with a publisher.publish(Event(...)) carrying the same information structurally. A mechanical, low-risk change: every log call site audited in §7–§8 becomes exactly one additional line.
  • Gorev2Orchestrator.run() gains explicit context.transition_to(phase, reason) calls at each §5 boundary — replacing current_state_text, which today exists only for the old Dashboard's HUD text and is used nowhere else.
  • MavsdkBackendBase.upload_mission() — beyond the functional fix already applied, gains the item-count assertion from §7.2 as the permanent regression guard for the §0 bug class.
  • CenteringController.go_to_and_center() — its return value must stop being discarded by the caller; a timeout becomes a BLOCKING_WAIT, not a silently-ignored False.
15

Logging architecture

Replaces mission_logger.py's three flat loggers (core, real_system, gz_system) with:

  • Structured, not string-formatted — log records are the same Event objects from §7, serialized as JSON Lines. Logging becomes a projection of the event stream, eliminating the risk of log text and actual state drifting apart — exactly what happened in both §0 bugs, where the logs “looked” like the system was working.
  • Correlation every event carries mission_id and, where applicable, correlation_id — one full target-acquisition attempt shares one ID, so a postmortem can filter to “everything that happened while pursuing target #2” in one query.
  • Retention one JSONL file per mission_id (not per process-restart timestamp), rotated only by mission boundary — always “everything that happened in this flight.”
16

Diagnostic architecture — the 60-second rule

The Presentation Layer must render, from MissionSnapshot alone, a single “Blocking Reason Panel” answering, without log-reading:

  1. Current phase, and how long it's been in that phase vs. expected max.
  2. blocking, if non-null: what it's waiting on, which subsystem owns it, elapsed, remaining time to timeout.
  3. HealthMatrix, filtered to non-Healthy entries only.
  4. Active watchdogs (§18) and remaining time.
  5. Last 10 events, most recent first, severity-marked.
  6. Interlock state, always visible regardless of phase — the single most safety-critical piece of state in the system.
What this panel would have shown, this engagement

Bug 1 — phase stuck at TARGET_TRACKING, far past expected duration, blocking.waiting_on = WAITING_TRACK_READY, with the three sub-conditions individually visible showing is_navigating_to: false never flipping — pointing directly at the missing call.

Bug 2 — MISSION_UPLOAD_CONFIRMED fires with upload_item_count: 0 against requested_item_count: 5 — a mismatch visible in under 5 seconds.

19

Mission replay capability

The Event Store is an append-only, ordered, complete JSONL record per mission_id. Replay is: read the file, feed events through the same MissionSnapshot-folding logic the live Aggregator uses, at recorded real-time pacing or accelerated. Replay and the live view are the same code path rendering the same data structure — no separate replay renderer to keep in sync, eliminating an entire class of “replay doesn't match what actually happened” bugs. This directly serves competition post-run debrief: reconstruct exactly what the state machine believed at every second of the flight, without the aircraft present.

20

Metrics & analytics

Derived entirely from the event stream, computed by an optional, non-blocking analytics subscriber:

  • Mission phase durations, actual vs. budgeted — trend across competition attempts.
  • Detection effective Hz vs. the 10–30 Hz spec band — currently unmeasured, closed here.
  • Confidence distribution of accepted vs. rejected detections — calibration signal for YOLO_CONFIDENCE_THRESHOLD=0.70.
  • Centering convergence time distribution.
  • Time from TRACK_READY to GPS_SAVE_CONFIRMED — the single most useful competition-performance number.
  • Payload release latency and verification success rate.
  • EventBus drop count — non-zero is itself a signal about the Ops Center's own capacity.
21

Future scalability

  • Multi-vehicle mission_id is already vehicle-scoped; a fleet moves the EventBus from in-process to a lightweight local broker, adding vehicle_id to the envelope. §5–§10's data model doesn't change shape, only cardinality.
  • Remote viewing a durable, ordered Event Store already makes a simple tail-and-forward bridge sufficient for a judge-facing display — no runtime redesign.
  • SearchPlanner strategies the §9.6 extraction is what allows a future QGC-sourced polygon strategy, or a coverage-optimized planner, without touching orchestration or observability at all.
